# UI 설계 작업 가이드

이 디렉터리는 GetUp의 UI를 구현하기 전에 로우파이와 하이파이 설계, 검토 결과, 구현 승인 근거를
기록한다. 설계 문서는 관련 `spec.md`, `plan.md`, `tasks.md`를 기준으로 작성하며 실제 위치 좌표나
`FamilyActivitySelection` token 같은 민감 정보는 포함하지 않는다.

## 디렉터리 구조

- `low-fidelity/`: 사용자 흐름, 화면 구조, 상태, 상호작용과 접근성 가설을 검증하는 문서
- `high-fidelity/`: 승인된 로우파이를 바탕으로 시각 명세, 전체 상태와 접근성을 확정하는 문서
- 각 디렉터리의 `TEMPLATE.md`: 사용자 스토리별 설계 기록을 시작할 때 복사하는 원본

## 필수 작업 순서

1. `low-fidelity/TEMPLATE.md`를 복사해 사용자 스토리별 문서를 만든다.
2. 로우파이 Figma node 링크, 사용자 흐름, 화면 상태, 검증 규칙과 접근성 가설을 기록한다.
3. 사용자 검토 결과를 반영하고 로우파이 승인 상태를 `승인됨`으로 기록한다.
4. 승인된 로우파이 문서를 연결해 `high-fidelity/TEMPLATE.md` 기반 문서를 만든다.
5. 하이파이에 색상, 서체, 간격, component 상태, 문구와 접근성 검증 결과를 기록한다.
6. 사용자 검토 결과를 반영하고 구현 승인 상태를 `승인됨`으로 기록한다.
7. 관련 SwiftUI 또는 shield UI task를 시작한다.

로우파이가 승인되기 전에는 하이파이를 시작하지 않으며, 하이파이가 승인되기 전에는 UI를
구현하지 않는다. 승인 뒤 제품 동작이나 화면 구조가 달라지면 해당 설계 단계로 돌아가 재검토한다.

## 문서 상태

| 상태 | 의미 | 다음 단계 진행 |
|---|---|---|
| `작성 전` | 설계 작업을 시작하지 않음 | 불가 |
| `검토 대기` | 검토할 수 있는 초안이 준비됨 | 불가 |
| `변경 요청` | 검토 의견 반영이 필요함 | 불가 |
| `승인됨` | 검토자가 다음 단계 진행을 승인함 | 가능 |

## 파일 이름

사용자 스토리와 목적을 알 수 있는 kebab-case 이름을 사용한다.

- `US1-rule-configuration.md`
- `US2-automatic-restriction.md`
- `US3-permission-recovery.md`
- `US4-uncertain-location.md`

하나의 사용자 스토리를 여러 문서로 나누면 뒤에 화면 또는 흐름 이름을 덧붙인다. Figma 링크는
가능하면 파일 홈이 아니라 검토할 frame 또는 section의 node 링크를 기록한다.

## 검토 기록 원칙

- 검토 날짜, 검토자, 결과, 의견과 반영 여부를 남긴다.
- `변경 요청` 의견은 반영 위치 또는 미반영 사유를 연결한다.
- 승인자는 이름과 승인 날짜를 직접 기록한다.
- 미해결 항목이 있으면 구현 영향과 후속 task를 명시한다.
- 접근성은 VoiceOver 읽기 순서와 label, Dynamic Type, 색상 외 상태 표현, 대비, Reduce Motion,
  focus 이동과 touch target을 설계 단계부터 확인한다.

## 구현 시작 전 확인

- 관련 로우파이와 하이파이 문서가 모두 존재한다.
- 두 문서의 승인 상태가 `승인됨`이다.
- 하이파이가 승인된 로우파이 문서를 참조한다.
- 화면의 정상·빈 상태·오류·권한 부족·불확실·loading·disabled 상태가 필요한 범위에서 정의됐다.
- 접근성 검증 결과와 알려진 예외가 기록됐다.
- 구현 대상 task와 파일이 하이파이 문서에 연결됐다.
