# GetUp Constitution

## Core Principles

### I. Specification-Driven Implementation
기능 구현은 승인된 기능 명세(spec)를 유일한 요구사항 기준으로 삼아야 한다(MUST).
구현 결과는 명세의 사용자 시나리오, 기능 요구사항, 성공 기준과 추적 가능해야 한다.
명세와 구현이 충돌하면 임의로 구현을 확장하지 않고, 먼저 명세를 수정하고 승인한 뒤
구현을 변경해야 한다. 이는 구현과 제품 의도 사이의 불일치를 방지하기 위함이다.

### II. Core Business Logic Testing
도메인 규칙, 상태 전이, 계산, 데이터 검증 등 핵심 비즈니스 로직에는 자동화된 테스트를
작성해야 한다(MUST). 테스트는 정상 경로뿐 아니라 명세에 정의된 주요 경계 조건과 실패
경로도 검증해야 한다. 핵심 로직의 변경은 해당 동작을 검증하는 테스트의 추가 또는 수정을
동반해야 한다. 이는 회귀를 조기에 발견하고 제품의 핵심 동작을 신뢰할 수 있게 하기 위함이다.

### III. Structural Change Documentation
모듈 경계, 데이터 흐름, 의존성 방향, 영속성 모델 또는 공개 인터페이스에 영향을 주는 중요한
구조 변경은 문서화해야 한다(MUST). 문서에는 변경 배경, 선택한 구조, 주요 대안과 기각 이유,
영향 범위 및 필요한 마이그레이션을 기록해야 한다. 문서는 변경된 코드와 같은 변경 단위에서
갱신되어야 한다. 이는 향후 유지보수자가 구조적 의사결정을 재구성할 수 있게 하기 위함이다.

### IV. Pre-Completion Test Gate
구현을 완료로 선언하기 전에 변경과 관련된 자동화 테스트를 실행해야 한다(MUST). 실패한 관련
테스트가 하나라도 있으면 구현은 완료로 간주할 수 없다. 환경 제약으로 테스트를 실행할 수 없는
경우 완료로 표현하지 않고, 실행하지 못한 테스트와 원인 및 수동 검증 결과를 명시해야 한다.
이는 완료 상태가 검증 가능한 증거에 근거하도록 보장하기 위함이다.

## Quality Standards

- 각 기능 요구사항은 구현 코드와 검증 수단으로 추적 가능해야 한다.
- 테스트는 결정적이고 반복 실행 가능해야 하며, 외부 상태에 불필요하게 의존해서는 안 된다.
- 구조 문서는 실제 구현과 일치해야 하며, 오래되거나 검증할 수 없는 설명을 남겨서는 안 된다.
- 단순한 표현 변경이나 기계적 수정은 핵심 로직 테스트 대상이 아닐 수 있으나, 테스트 생략 근거가
  변경 범위에서 명확해야 한다.

## Development Workflow

1. 구현 전 현재 기능 명세와 수용 기준을 확인한다.
2. 변경 대상 중 핵심 비즈니스 로직과 필요한 테스트 범위를 식별한다.
3. 명세에 맞게 구현하고, 핵심 로직 테스트를 작성하거나 갱신한다.
4. 중요한 구조 변경이 있으면 같은 변경 단위에서 설계 문서를 갱신한다.
5. 완료 전 관련 테스트를 실행하고 결과를 검토한다.
6. 리뷰에서는 명세 추적성, 핵심 테스트, 구조 문서 및 테스트 실행 증거를 확인한다.

## Governance

이 헌법은 GetUp 프로젝트의 다른 개발 관행보다 우선한다. 모든 기능 명세, 구현 계획, 작업 목록,
코드 리뷰는 본 원칙 준수 여부를 확인해야 한다.

헌법 개정은 변경 사유와 영향을 문서화하고 프로젝트 책임자의 승인을 받아야 한다. 기존 원칙을
제거하거나 호환되지 않게 재정의하면 MAJOR, 원칙이나 필수 지침을 추가 또는 실질적으로 확장하면
MINOR, 의미를 바꾸지 않는 명확화와 문구 수정은 PATCH 버전을 올린다.

각 구현 완료 시 관련 테스트 실행 결과를 검토하고, 중요한 구조 변경이 있는 경우 문서 갱신을
확인해야 한다. 원칙을 예외 처리하려면 예외 범위, 사유, 위험, 종료 조건을 변경 기록에 명시하고
프로젝트 책임자의 승인을 받아야 한다.
